## 2. Проверка по разделам спецификации

### 2.1 Goals (G1-G4)

#### ✅ G1: Upload flow
- **Требование:** админ загружает файл → создаётся запись `media_assets` → файл уходит в S3 → возвращается публичный URL
- **Реализация:** 
  - `CreateMediaAssetUseCase` создает запись в БД и генерирует pre-signed URL
  - `FinalizeMediaUploadUseCase` подтверждает загрузку и устанавливает публичный URL
  - **Статус:** ✅ Полностью реализовано

#### ✅ G2: Права доступа
- **Требование:** загрузка только admin roles; удаление с проверкой "используется ли в контенте"
- **Реализация:**
  - RBAC проверка через `RbacGuard.requireContentManager()` (owner/editor)
  - Проверка использования через `isUsedInContent()` в `DeleteMediaAssetUseCase`
  - Поддержка `force=true` для принудительного удаления
  - **Статус:** ✅ Полностью реализовано

#### ✅ G3: Поддержка типов
- **Требование:** `image/*`, `audio/*`, `application/pdf`
- **Реализация:**
  - `MediaType` value object с поддержкой всех трех типов
  - Валидация через `MediaType.fromMimeType()`
  - **Статус:** ✅ Полностью реализовано

#### ✅ G4: Метаданные
- **Требование:** title, alt_text, mime, size, object_key
- **Реализация:**
  - Все поля присутствуют в `MediaAsset` aggregate
  - Сохраняются в БД через `PrismaMediaAssetRepository`
  - **Статус:** ✅ Полностью реализовано

### 2.2 Acceptance Criteria (AC-1 - AC-4)

#### ✅ AC-1: API для получения pre-signed upload URL
- **Требование:** Есть API для получения pre-signed upload URL (или proxy upload)
- **Реализация:**
  - Endpoint: `POST /api/admin/media/init`
  - Возвращает `{ mediaAssetId, uploadUrl, expiresAt }`
  - Использует `S3StorageService.generateUploadUrl()` с TTL 1 час
  - **Статус:** ✅ Полностью реализовано

#### ✅ AC-2: Валидация mime/размера до загрузки
- **Требование:** Файл проверяется по mime/размеру до загрузки
- **Реализация:**
  - Валидация MIME типа в `CreateMediaAssetUseCase.execute()`
  - Валидация размера через `MediaType.getMaxSizeBytes()`:
    - Image: 10 MB
    - Audio: 50 MB
    - PDF: 20 MB
  - Проверка в `MediaAsset.create()` (domain layer)
  - **Статус:** ✅ Полностью реализовано

#### ✅ AC-3: Связь записи в БД с объектом в S3
- **Требование:** После загрузки запись в БД связана с объектом в S3
- **Реализация:**
  - `objectKey` генерируется сервером через `ObjectKey.generate()`
  - Формат: `{mediaType}/{year}/{month}/{uuid}-{filename}`
  - Сохраняется в БД при создании
  - Публичный URL генерируется через `S3StorageService.generatePublicUrl()`
  - **Статус:** ✅ Полностью реализовано

#### ✅ AC-4: Удаление с проверкой использования
- **Требование:** Удаление медиа запрещено, если есть ссылки из контента (или требует forced unlink)
- **Реализация:**
  - Проверка через `PrismaMediaAssetRepository.isUsedInContent()`
  - Запрет удаления если используется (без `force=true`)
  - Поддержка `force=true` для принудительного удаления
  - **Статус:** ✅ Полностью реализовано

### 2.3 Негативные сценарии (NS-1, NS-2)

#### ✅ NS-1: Неподдерживаемый тип файла
- **Требование:** Неподдерживаемый тип файла → 400, без загрузки
- **Реализация:**
  - Валидация в `CreateMediaAssetUseCase.execute()`
  - Выбрасывается `ValidationError` с кодом 400
  - Запись в БД не создается
  - **Статус:** ✅ Полностью реализовано
  - **Тесты:** ✅ Покрыто в `media.integration.test.ts`

#### ⚠️ NS-2: S3 недоступен
- **Требование:** S3 недоступен → корректная ошибка, без "битых" записей (или transactional cleanup)
- **Реализация:**
  - Ошибки S3 обрабатываются в `S3StorageService`
  - При ошибке генерации upload URL выбрасывается исключение
  - **Замечание:** Нет явной транзакционной очистки при ошибке S3 после создания записи
  - **Рекомендация:** Рассмотреть добавление транзакционной логики или фоновой очистки "битых" записей
  - **Статус:** ⚠️ Частично реализовано (требует улучшения)
